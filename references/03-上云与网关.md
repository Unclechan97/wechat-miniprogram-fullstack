# 03 · 上云与网关（callContainer 深水区）

## 3.1 云托管开通（控制台）

1. cloud.weixin.qq.com → 云托管 → 新建环境（区域选离用户近的，如华东上海）
2. 新建服务（如 `myapp-api`），首部署可以先用"本地代码包上传"跑通
3. **环境变量**在 服务设置里配（不要塞进代码包）。最小清单：

| 变量 | 值 | 说明 |
|---|---|---|
| `PORT` | `3000` | 与容器端口/映射一致 |
| `MYSQL_HOST` | 控制台的 `host`（或 `host:port` 整串） | config 已兼容整串粘贴 |
| `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` | 建库时设置 | |
| `APP_SHARED_KEY` | 随机长串（与小程序端 config 一致） | 开放端点共享密钥 |
| `ALLOW_MOCK_IDENTITY` | **`false`（或不设）** | ★ 生产必须关——否则任何人伪造 `X-User-Id` 头即可冒充他人（见 §3.4 安全说明） |
4. 建议配置：
   - **最小实例数 ≥ 1**：默认缩零（缩到 0 实例），下次请求要冷启动等十几秒；常驻 1 实例是稳定体验的底线
   - **容器规格**：见 3.4，别省那点钱选 0.25 核

## 3.2 从没碰过云托管？先理解调用方式

**★ 前置条件（缺一个 callContainer 就直接 fail，实测踩坑；报"云能力未初始化/环境不存在"类错误时先查这三条，别误判成 -606001）**：

1. `app.ts` 的 `onLaunch` 里必须先 `wx.cloud.init({ env: '环境ID' })`（全项目一次；骨架模板已含）
2. 基础库 ≥ **2.23.0**（callContainer 下限）——不光工具里调，还要在 mp 后台「设置 → 基本设置 → 基础库最低版本设置」把线上最低版本也设为 ≥2.23.0
3. 小程序要与云托管环境**完成关联**（一般在云托管控制台的环境/服务设置里添加小程序 AppID；不同界面版本位置不同，以控制台提示为准）

小程序端调用两种通道：

```ts
// ① callContainer：免自有域名/域名备案，网关自动注入 x-wx-openid
wx.cloud.callContainer({
  config: { env: '你的环境ID' },
  path: '/api/xxx',
  method: 'POST',
  header: { 'X-WX-SERVICE': 'your-service-name' },  // ★ 必带，缺了报 INVALID_PATH
  data: {...},
  success: (r) => {...},
});

// ② 公网域名：控制台开启"公网访问"后可直接 HTTPS 调用（可用于直连/调试）
// https://<service>-<envidHash>.sh.run.tcloudbase.com/api/xxx
// ⚠ 此域名不允许加入小程序"服务器域名"白名单（仅测试用），正式版依赖 callContainer
```

**callContainer 限制清单（全部实测）**：

| 限制 | 表现 | 对策 |
|---|---|---|
| 不支持 multipart | 文件无法直接上传 | JSON base64 传文件（express.json limit 提到 3mb） |
| 大包体被拒 | 大图 base64（2-3MB）报 **-606001** | 上传前压缩：`wx.compressImage` 长边 1280px/quality 60，目标 ≤1.2MB，超了再压一轮 |
| 网关频控/拒客 | 突发 -606001 system error | 减少调用次数 + 客户端重试 + 幂等键（见 3.5） |
| 无日志命令 | CLI 无日志查询 | 排障靠公网域名 curl + 控制台日志面板 |

## 3.3 ★ -606001 诊断方法论（值得单独背下来）

**定义**：`cloud.callContainer:fail -606001 system error` = **网关层拒绝，请求根本没到容器**。特征是突发（数秒~1分钟）、恢复后一切正常、容器日志里没有对应记录。

**第一步：区分"容器问题"还是"网关问题"** —— 直连公网域名压测对照：

```bash
# 完整脚本见 templates/direct-stress.mjs（已参数化，无内置文件依赖）：
DIRECT_BASE=https://<服务>-<hash>.sh.run.tcloudbase.com \
STRESS_PATH=/api/asr STRESS_BODY_FILE=./body.json node direct-stress.mjs 10
# 连打 10 次，看成功率与延迟
```

- 直连 10/10 全过、延迟正常 → **网关问题**（容器无辜），进入第二步
- 直连也挂 → 容器问题：看内存/CPU（ffmpeg 爆内存会被杀重启）、代码崩溃

**第二步：排查触发条件（控制变量）**
- 是不是**每次都在同一个端点**挂？（大包体？耗 CPU？）→ 包体/计算量问题
- 是不是**容器刚启动时易发**？→ 冷启动/负载问题
- 是不是**单位时间请求多时才发**？→ 频控
- 容器规格多大？→ **0.25核0.5G 在 CPU 打满时网关会拒客**；升 1核2G 实测 -606001 消失

**第三步：按结论选解法（可组合）**

| 解法 | 做法 | 适用 |
|---|---|---|
| ① 加规格 | 控制台改 1核2G（约 ¥60/月） | 计算型端点（ffmpeg/AI）导致的拒客 |
| ② 减少请求数 | 合并响应（一次录音=识别+解析一次返回；保存响应捎带汇总） | 频控型 |
| ③ 重试+幂等 | 客户端 2s/6s/12s 梯度重试；写接口带 client_token 幂等 | 所有场景兜底 |
| ④ 直连通道 | 开放端点走公网直连，失败自动回退 callContainer | 高频/大包体端点 |

## 3.4 ★ 直连通道设计（重流量端点终局方案）

**背景**：语音/图片这类重流量端点，即使加了规格也偶尔被网关抽风波及；公网直连可以完全绕开网关频控。

**适用条件**：端点**不依赖微信身份**（纯计算/外部 API 代理），如 ASR/TTS/图片解析。

**安全设计**：公网暴露必须防滥用——共享密钥头：

```ts
// server: 只拦截开放端点，错密钥 401
const OPEN_PATH_RE = /^\/api\/(asr|tts|parse)(\/|$)/;
export function openApiGuard(req, res, next) {
  if (!OPEN_PATH_RE.test(req.path)) return next();
  if (req.header('x-app-key') === config.appSharedKey) return next();
  return res.status(401).json({ error: '未授权的访问' });
}
```

> 密钥内置小程序源码只能防"第三方蹭配额"，不是身份凭证（源码可被提取）。真正的账本数据永远走 callContainer 的 openid，不依赖此密钥。损失上限 = 第三方盗刷你的 ASR/TTS 配额，可接受。

**★ 公网直连 + 身份安全（必读）**：容器一旦开启「公网访问」，`x-wx-openid` 头**外部可以自行伪造**，所以——

- **身份类端点绝不能走公网直连**，只走 callContainer（网关真注入，不可伪造）
- 开放端点（不依赖身份）才允许直连，靠共享密钥 + 配额止损
- 服务端身份解析统一走 `resolveUserId(req)`（片段见 02 §2.1）：openid 优先，`X-User-Id` 模拟仅在 `ALLOW_MOCK_IDENTITY=true` 时启用，**生产环境变量必须为 false**

**客户端策略（直连优先 + 静默回退）**：

```ts
async function openRequest(method, url, data) {
  if (API_MODE === 'cloud' && DIRECT_BASE) {
    try {
      return await directRequest(method, url, data);   // 直连
    } catch (e) {
      const status = e.statusCode;
      if (status && status < 500) throw e;             // 4xx=服务端拒绝，通道是通的，不回退
      console.warn('[api] 直连失败，回退 callContainer:', ...);
    }
  }
  return request(method, url, data);                   // 回退（自带 gatewayRetry）
}
```

**三通道上传（文件）**：直连 multipart（省 1/3 体积）→ 回退 callContainer JSON base64；本地开发走 wx.uploadFile。

**★ 回退通道必须也带密钥头**——真机实测踩坑：直连被域名校验拦 → 回退 callContainer → 服务端 guard 因缺 `x-app-key` 拒了 → 用户看到"未授权访问"。**统一请求头构造函数，所有通道共用**。

## 3.5 抗频控组合拳（每层都别省）

1. **减少调用数**：一次业务操作=最少的网关调用（如语音记账：ASR 响应捎带文本解析结果、保存响应捎带月度汇总 → 5 次变 2 次）
2. **客户端重试**：`delays = [2000, 6000, 12000]`，只对网关类错误（`/-606\d{3}|system ?error/i`）重试，只在 cloud 模式
3. **幂等键**：写接口 `client_token`（客户端生成 `v-<时间戳>-<随机>`），服务端 `WHERE user_id=? AND client_token=?` 查重，命中直接返回原 id
4. **客户端缓存**：TTS 音频等静态内容本地缓存（Map + 上限），常用短语零网络
5. **格式优化**：能 multipart 不 base64；能压缩先压缩

## 3.6 云托管 MySQL（serverless）

- **开通入口**：云托管控制台 → 数据库 → 新建 MySQL（serverless）；连接信息（`host:port`、用户、密码）在实例页，建好后把值配到服务环境变量（见 §3.1）
- 存算分离，**10 分钟无连接自动暂停**（compute=0，≈1-5 元/月）
- 唤醒需几秒~几十秒 → 数据层瞬时错误自动重试（`resuming`/`ECONNREFUSED` 等）是必备能力
- 连接串格式：控制台给 `host:port`，config 解析要兼容整串粘贴
- **首部署特别注意**：`initDb` 成功才 `listen`，首次冷启可能要等 30s+，日志里"数据库暂不可用，重试中"是正常现象
